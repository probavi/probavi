# Probavi Roadmap

Order matters. Each phase has an explicit exit criterion; do not start the next phase before meeting it. The two specifications in Phase 0 are the foundation everything else depends on — rushing them is the most expensive mistake available.

**Goal:** the two load-bearing specifications exist and have survived review.

## Phase 2 — Prove the abstractions

**Goal:** demonstrate that both extension axes (engines, sandboxes) work without touching the core.

- [x] Second adapter: MySQL/MariaDB (`mysqldump` + one physical-backup source). **Test of the protocol: if the core needs changes, fix the protocol now — it is still cheap.** **Complete 2026-07-31 (`adapters/mysql`: `mysqldump` + `mysqldump_dir` logical, Percona XtraBackup physical) with zero core changes. The protocol passed its test: the dialect difference (MySQL rejects SQL-standard quoted identifiers) is absorbed declaratively by the adapter's `sql_runner` template (`ANSI_QUOTES` via `--init-command`), and the physical flow reuses the idle-sandbox pattern with an `--init-file` auth reset mirroring the postgres adapter's pg_hba trust overwrite. Both paths proven end to end against real Docker.**
- [x] Point-in-time recovery drills: "restore to yesterday 14:32" for Postgres (WAL replay via wal-g or pgBackRest). Complete 2026-08-01: `target.pitr` config (`target_time` | `target_age`), core-side resolution + per-source capability gate (protocol already specified `pitr` in v0), evidence schema v1 records the resolved target as `drill.pitr_target`, postgres adapter drives `pgbackrest --type=time --target-action=promote` and waits recovery out; end-to-end PITR drill test proves batch-B exclusion and writability.
- [x] Second sandbox provider: Kubernetes Job **or** remote host over SSH (pick based on user demand). **Maintainer picked Kubernetes Job (2026-08-01). Complete 2026-08-01: `internal/sandbox/k8s` — each sandbox is a `batch/v1` Job driven through the kubectl CLI (no client-go, matching the docker provider's no-SDK rule; shared subprocess plumbing extracted to `internal/sandbox/cli`). Cluster-side cleanup backstop the docker provider cannot offer: `activeDeadlineSeconds` + `ttlSecondsAfterFinished` kill and garbage-collect a sandbox even if the drill host dies permanently; the host-scoped orphan sweep handles the normal case. Security: no service-account token, no ports, seccomp RuntimeDefault; pod-level network isolation is the cluster's NetworkPolicy job (documented residual difference vs. docker's `--network none`). Second axis proven: the unchanged postgres adapter restores a real pg_dump into a kind cluster end to end — zero core changes, zero adapter changes. CI runs the k8s suite against kind. Addendum 2026-08-01: the docker provider is hardened for remote daemons over the CLI's native SSH transport (`DOCKER_HOST=ssh://…`) — host-scoped sweep labels make shared daemons safe, CI proves the path over a real SSH loopback; the SSH endpoint stays in the environment because sandbox params enter signed evidence (schema §8).**
- [x] Restore-duration trend data surfaced in metrics; alert-friendly derived metrics (e.g. rolling P95 restore time). **Complete 2026-08-01: no daemon (non-goal), so the trend is recomputed after every drill from the canonical history — the evidence log itself. `probavi_restore_duration_rolling_seconds{quantile="0.5"|"0.95"|"1"}` (nearest-rank over the last 100 completed restores of the drill) plus `probavi_restore_trend_samples`, rendered into the same node_exporter textfile; README documents the two alert rules that cover staleness and RTO drift. Zero new config keys, zero evidence changes.**
- [x] Adapter developer guide + conformance test suite (`probavi adapter conformance <cmd>`), so third parties can build adapters confidently. **Complete 2026-08-01: the §10 check list is frozen in `docs/adapter-protocol.md` (15 checks: framing discipline, handshake, error-registry mapping, timing plausibility, teardown idempotence, SIGTERM handling) and implemented in `internal/conformance` — a deliberately independent second implementation of the protocol driving a simulated sandbox, no container runtime needed. Suite tests prove every check fails against 15 scripted violation modes of a fake adapter and passes 15/15 against both in-repo adapters (which the suite immediately improved: their handshake now returns the §3.1-mandated `detail.supported`). Guide: `docs/adapter-development.md`.**

**Exit criterion:** adding engine #3 requires zero core changes; an externally-authored adapter passes conformance.

## Phase 3 — The differentiating layer

**Goal:** turn verified runs into organisational trust.

**Open-core boundary (decided 2026-07-31, restated 2026-08-04):** proving that backups restore stays free forever — the CLI, adapters, sandbox providers, checks, evidence chain, `evidence verify`, metrics, notifications, and **DR game-days**, all Apache-2.0 in this repository. The line is not drawn at scale: a game-day is multi-database, dependency-ordered orchestration and is a full free feature, because proving that a whole service comes back is the product, not a tier of it. (The original wording said "proving a single drill stays free" — written before game-days existed, and it read as if orchestration were the upsell.) The organisational layer below — fleet dashboard, audit report export, RTO/RPO objectives and trends, SSO/RBAC — will be offered commercially, built on top of this open core and documented transparently when Phase 3 starts. The evidence spec and the independent verifier are never commercial.

Built commercially, **outside this repository** — listed here so the boundary is legible, not as work planned in this tree:

- Fleet dashboard (read-only web UI over the evidence store): estate-wide recoverability status, trends, drill calendar.
- Audit report export (HTML/PDF): "in the last 90 days, N drills across M databases, success rate, measured RTO distribution" — mapped to DORA / NIS2 / NIST expectations (see AGENTS.md §Compliance).
- RTO/RPO objectives in config; automatic breach detection and trend-based early warning ("restore time will exceed your RTO within ~6 months at current growth").

Work planned in this repository:
- [x] Publish the evidence format as a standalone versioned spec with an independent verifier tool. **Complete 2026-08-02 (`spec/evidence`, spec §12): the format was already versioned independently of the binary and frozen, so the gap was that verification was circular — the only thing checking the hash chain and signatures was the code that wrote them. Closed with a second implementation written from `docs/evidence-schema.md` alone, in a separate Go module with zero dependencies, which means the toolchain (not discipline) forbids it importing `internal/evidence`. Ships as `go install`-able `probavi-evidence-verify` with the §9 exit codes. The worked example moved out of `internal/evidence/testdata/` to `docs/schemas/evidence/examples/` and is now a published conformance vector: the core pins that it emits exactly those bytes, the verifier pins that an implementation which has never seen the core accepts them, and neither imports the other. Both agree on both published schema versions and on tampered input, down to the failing line. Library at 100% statement coverage, gated separately in CI.**

- [x] Get evidence off the host that produced it, without a shared filesystem or credentials on every machine. **Complete 2026-08-24 (`probavi push`, `internal/push`, spec `docs/evidence-push.md`, protocol `probavi-evidence-push/1`): one outbound HTTPS request, which a host behind NAT or in a DMZ has even when it has neither of the two usual answers. The whole file goes every time — that is what removes the state, and what makes a push idempotent and self-healing, since whatever an earlier one missed the next repairs — as `application/x-ndjson` to `<--to>/<--path>`, bearer token from the environment, optional HMAC in the notification's own header and scheme so one receiver verifies both. A push is a copy: the log is opened read-only, never modified or deleted, no flag offers otherwise, and a delivery failure (exit 2) never changes what a drill proved. Free like everything that proves and verifies restores, and deliberately receiver-agnostic: the core defines, endorses and requires no receiver, and because the bytes on the wire are the log itself, whoever holds them verifies with the public key the operator publishes — a delivery proves nothing on its own.**

**Exit criterion:** a compliance officer can hand an Probavi report to an auditor without editing it.

The grouping below is what the architecture makes cheap, not the popularity ranking, and the non-goal at the foot of this file still binds: **at most one new engine per release cycle**. An adapter nobody keeps green is worse than one that does not exist — the product is the evidence, and a stale engine claim is a false claim. Three questions the catalog raises are one-way doors, each to be answered before the first engine that needs it rather than during it:
  - *Privileged sandboxes.* The docker descriptor exposes `image`, `network`, `command`, `memory`, `cpus` and env — no `--privileged`, no sysctl. Db2's official image requires the first; Elasticsearch and OpenSearch want `vm.max_map_count=262144`. Either the descriptor grows a parameter — and the zero-ingress default grows a hole that every signed record then carries — or those engines are documented as out of reach on this provider. **Decided 2026-08-16: no sandbox descriptor grows a sysctl or privileged parameter — and the dilemma as written did not exist. `vm.max_map_count` is not a namespaced sysctl, so a per-container parameter is not a trade-off but an impossibility (measured: docker refuses `--sysctl vm.max_map_count=…` outright); it exists only host-wide, outside any sandbox's reach. The engines that motivated it need no sysctl in this sandbox at all: a single node bound to loopback runs in dev mode (bootstrap checks not enforced), and `node.store.allow_mmap: false` removes the mmap dependency by construction — OpenSearch 3.8 measured green under `--network none` with a 512M heap and no sysctl anywhere; the Elasticsearch leg of the same design is proven by its future adapter's CI matrix job, whose stock-kernel runners ship the default 65530 map count, exactly the environment the old advice raised. The adapter READMEs must state the trade — niofs instead of the mmap-hybrid store; a drill proves restorability, not production IO tuning. `--privileged` stays shut: it would dissolve the zero-ingress isolation every signed record leans on, so Db2 remains documented out of reach on this provider.**
  - *Built-in checks without SQL.* `internal/checks` composes `SELECT count(*) …` and `SELECT max(…) …` and hands the text to the adapter's `sql_runner`. MongoDB already documents the consequence: the generating built-ins do not apply and checks are raw `mongosh` expressions. Every non-SQL engine below inherits that. Accept it, or let an adapter declare templates for the built-in kinds — a protocol change, so a spec PR first.
  - *Backups that live in object storage.* The sandbox verbs are `exec` and `put_file` and the default network is `none`, so a drill reads what is on the local filesystem. InfluxDB 3, Milvus, Doris and CockroachDB put their backups in a bucket by default. Either staging stays the operator's documented job, or the source contract grows.
  - [x] **Supported engine-version matrix — first, because it shapes every adapter below.** Each `adapters/<id>/adapter.json` carries a single `verified` entry today (postgres 16, mysql 8.4, mongodb 7, mssql 2022), and `docs/capabilities.md` forbids rendering it as a supported range. Covering each engine's still-supported window instead takes those four alone from 4 image-versions to 19, and the whole catalog to roughly 100 — hours of integration time, so per-PR runs keep a pinned subset while the full matrix runs on a schedule and gates every release tag.   - [x] Oracle Database — RMAN and Data Pump are both in the Free edition; the cost is the container (slow start, 2 GB floor), and the community image may be the pragmatic verification target. **Complete 2026-08-21 (`adapters/oracle` 0.1.0) — the eighteenth engine, rank 1 of the DB-Engines lens above, shipped with a Data Pump source kind (`oracle_datapump`: one `expdp` dump file, imported into the image's pluggable database) after a measurement day that corrected every guess in this line.** The official image — not a community one — pulls anonymously from Oracle's registry and is the verification target (`database/free:23.26.3.0`, by then renamed "Oracle AI Database 26ai Free"); its `-lite` variant cannot run Data Pump at all (no `impdp`, XML component removed, measured), so the full 10 GB image is the cost. Three measured facts shaped the adapter.   - [ ] InfluxDB 3 Core — no backup command exists at all: the backup is a consistent copy of the object store, so what "consistent" means operationally has to be established before a drill can claim anything.

  - [ ] The structurally unreachable classes the DB-Engines lens names above — cloud-only services, query engines without storage, caches and embedded libraries, desktop products — are refused as classes rather than one by one: an adapter needs an engine that runs in a sandbox from an artifact the operator holds, and none of them has one. ## Deliberate non-goals (all phases)

No backup engine. No built-in scheduler (cron/systemd-timer + lock file + timeout is the way). No daemon on database hosts. No web interface. No secrets management beyond reading credentials from env/file for the duration of one drill or one push. No telemetry and no phone-home. No more than one new engine per release cycle.

The list is closed, and none of it is qualified with "yet", "unless proven unavoidable" or "before Phase 3": a non-goal with an escape clause is a roadmap item. `AGENTS.md` §2.4 carries the same list. `docs/capabilities.json` carries the six that describe the software; the engine rate limit is a release-cadence rule rather than a capability, so it has no entry there.

Every "no" protects the quality of the core.
