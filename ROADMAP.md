# Probavi Roadmap

Order matters. Each phase has an explicit exit criterion; do not start the next phase before meeting it. The two specifications in Phase 0 are the foundation everything else depends on — rushing them is the most expensive mistake available.

## Phase 0 — Contracts before code

**Goal:** the two load-bearing specifications exist and have survived review.

- [x] Choose project name: **Probavi** (Latin: "I have proven"). Pre-checked 2026-07-30: npm, PyPI, crates.io free; zero exact-name GitHub repos; no company hits in web search.
- [x] Canonical domain: **probavi.dev registered 2026-07-31.**
- [x] Choose license and add `LICENSE`. **Decided 2026-07-31: open-core model. This repository (the core) is Apache-2.0; Phase 3 organisational features will be offered commercially, developed outside this repository. The evidence format spec and the independent verifier stay freely available forever — paywalling verification would destroy the trust proposition. Contributions: DCO.**
- [x] Write `docs/adapter-protocol.md` v0: JSON-over-stdio protocol with four operations — `probe`, `provision`, `healthcheck`, `teardown` — including full example request/response messages, error model, timeout semantics, and versioning rules. **Approved 2026-07-31 (core-mediated sandbox-verb model); normative. Frozen 2026-08-01: conformance check list in §10, machine-readable JSON Schemas in `docs/schemas/adapter/`, CI-verified against the golden files (`internal/spec`).**
- [x] Write `docs/evidence-schema.md` v0: record fields, canonical JSON serialization, hash-chain construction, ed25519 signing, verification procedure. **Approved 2026-07-31 (RFC 8785 JCS restricted to integer-only numbers); normative, current version v1 (2026-08-01, `drill.pitr_target`). ## Phase 2 — Prove the abstractions

**Goal:** demonstrate that both extension axes (engines, sandboxes) work without touching the core.

- [x] Second adapter: MySQL/MariaDB (`mysqldump` + one physical-backup source). **Test of the protocol: if the core needs changes, fix the protocol now — it is still cheap.** **Complete 2026-07-31 (`adapters/mysql`: `mysqldump` + `mysqldump_dir` logical, Percona XtraBackup physical) with zero core changes. The protocol passed its test: the dialect difference (MySQL rejects SQL-standard quoted identifiers) is absorbed declaratively by the adapter's `sql_runner` template (`ANSI_QUOTES` via `--init-command`), and the physical flow reuses the idle-sandbox pattern with an `--init-file` auth reset mirroring the postgres adapter's pg_hba trust overwrite. Both paths proven end to end against real Docker.**
- [x] Point-in-time recovery drills: "restore to yesterday 14:32" for Postgres (WAL replay via wal-g or pgBackRest). Complete 2026-08-01: `target.pitr` config (`target_time` | `target_age`), core-side resolution + per-source capability gate (protocol already specified `pitr` in v0), evidence schema v1 records the resolved target as `drill.pitr_target`, postgres adapter drives `pgbackrest --type=time --target-action=promote` and waits recovery out; end-to-end PITR drill test proves batch-B exclusion and writability.
- [x] Second sandbox provider: Kubernetes Job **or** remote host over SSH (pick based on user demand). **Maintainer picked Kubernetes Job (2026-08-01). Complete 2026-08-01: `internal/sandbox/k8s` — each sandbox is a `batch/v1` Job driven through the kubectl CLI (no client-go, matching the docker provider's no-SDK rule; shared subprocess plumbing extracted to `internal/sandbox/cli`). - [x] Restore-duration trend data surfaced in metrics; alert-friendly derived metrics (e.g. rolling P95 restore time). **Complete 2026-08-01: no daemon (non-goal), so the trend is recomputed after every drill from the canonical history — the evidence log itself. `probavi_restore_duration_rolling_seconds{quantile="0.5"|"0.95"|"1"}` (nearest-rank over the last 100 completed restores of the drill) plus `probavi_restore_trend_samples`, rendered into the same node_exporter textfile; README documents the two alert rules that cover staleness and RTO drift. Zero new config keys, zero evidence changes.**
- [x] Adapter developer guide + conformance test suite (`probavi adapter conformance <cmd>`), so third parties can build adapters confidently. **Complete 2026-08-01: the §10 check list is frozen in `docs/adapter-protocol.md` (15 checks: framing discipline, handshake, error-registry mapping, timing plausibility, teardown idempotence, SIGTERM handling) and implemented in `internal/conformance` — a deliberately independent second implementation of the protocol driving a simulated sandbox, no container runtime needed. Guide: `docs/adapter-development.md`.**

**Exit criterion:** adding engine #3 requires zero core changes; an externally-authored adapter passes conformance.

## Phase 3 — The differentiating layer

**Goal:** turn verified runs into organisational trust.

**Open-core boundary (decided 2026-07-31, restated 2026-08-04):** proving that backups restore stays free forever — the CLI, adapters, sandbox providers, checks, evidence chain, `evidence verify`, metrics, notifications, and **DR game-days**, all Apache-2.0 in this repository. The line is not drawn at scale: a game-day is multi-database, dependency-ordered orchestration and is a full free feature, because proving that a whole service comes back is the product, not a tier of it. (The original wording said "proving a single drill stays free" — written before game-days existed, and it read as if orchestration were the upsell.) The organisational layer below — fleet dashboard, audit report export, RTO/RPO objectives and trends, SSO/RBAC — will be offered commercially, built on top of this open core and documented transparently when Phase 3 starts. The evidence spec and the independent verifier are never commercial.

- [ ] Fleet dashboard (read-only web UI over the evidence store): estate-wide recoverability status, trends, drill calendar.
- [ ] Audit report export (HTML/PDF): "in the last 90 days, N drills across M databases, success rate, measured RTO distribution" — mapped to DORA / NIS2 / NIST expectations (see AGENTS.md §Compliance).
- [ ] RTO/RPO objectives in config; automatic breach detection and trend-based early warning ("restore time will exceed your RTO within ~6 months at current growth").
- [x] Publish the evidence format as a standalone versioned spec with an independent verifier tool. **Complete 2026-08-02 (`spec/evidence`, spec §12): the format was already versioned independently of the binary and frozen, so the gap was that verification was circular — the only thing checking the hash chain and signatures was the code that wrote them. Closed with a second implementation written from `docs/evidence-schema.md` alone, in a separate Go module with zero dependencies, which means the toolchain (not discipline) forbids it importing `internal/evidence`. Ships as `go install`-able `probavi-evidence-verify` with the §9 exit codes. The worked example moved out of `internal/evidence/testdata/` to `docs/schemas/evidence/examples/` and is now a published conformance vector: the core pins that it emits exactly those bytes, the verifier pins that an implementation which has never seen the core accepts them, and neither imports the other. Both agree on both published schema versions and on tampered input, down to the failing line. Library at 100% statement coverage, gated separately in CI.**

**Exit criterion:** a compliance officer can hand an Probavi report to an auditor without editing it.

- [ ] **Engine catalog.** Recorded 2026-08-14 from a maintainer-supplied survey of 43 engines, four of which already ship (PostgreSQL, MySQL, MongoDB, SQL Server). The grouping below is what the architecture makes cheap, not the popularity ranking, and the non-goal at the foot of this file still binds: **at most one new engine per release cycle**. An adapter nobody keeps green is worse than one that does not exist — the product is the evidence, and a stale engine claim is a false claim. Three questions the catalog raises are one-way doors, each to be answered before the first engine that needs it rather than during it:
  - *Privileged sandboxes.* The docker descriptor exposes `image`, `network`, `command`, `memory`, `cpus` and env — no `--privileged`, no sysctl. Db2's official image requires the first; Elasticsearch and OpenSearch want `vm.max_map_count=262144`. Either the descriptor grows a parameter — and the zero-ingress default grows a hole that every signed record then carries — or those engines are documented as out of reach on this provider.
  - *Built-in checks without SQL.* `internal/checks` composes `SELECT count(*) …` and `SELECT max(…) …` and hands the text to the adapter's `sql_runner`. MongoDB already documents the consequence: the generating built-ins do not apply and checks are raw `mongosh` expressions. Every non-SQL engine below inherits that. Accept it, or let an adapter declare templates for the built-in kinds — a protocol change, so a spec PR first.
  - *Backups that live in object storage.* The sandbox verbs are `exec` and `put_file` and the default network is `none`, so a drill reads what is on the local filesystem. InfluxDB 3, Milvus, Doris and CockroachDB put their backups in a bucket by default. Either staging stays the operator's documented job, or the source contract grows.
  - [x] **Supported engine-version matrix — first, because it shapes every adapter below.** Each `adapters/<id>/adapter.json` carries a single `verified` entry today (postgres 16, mysql 8.4, mongodb 7, mssql 2022), and `docs/capabilities.md` forbids rendering it as a supported range. Covering each engine's still-supported window instead takes those four alone from 4 image-versions to 19, and the whole catalog to roughly 100 — hours of integration time, so per-PR runs keep a pinned subset while the full matrix runs on a schedule and gates every release tag. Physical restores make this correctness rather than test hygiene: a physical backup only restores into its own major, so an adapter that can read the version out of the backup should compare it to the running engine and say so, instead of letting the engine fail cryptically. **Complete 2026-08-14 (PR #119; policy in `docs/engine-versions.md`, normative). The manifest drives both the claim and the job: each `verified` list marks exactly one `baseline` image that every push restores from, the full list runs in a generated matrix (`.github/workflows/version-matrix.yml`) weekly, on any PR touching a manifest, and before every release tag; a test fails when the jobs and the published claims disagree in either direction, and the integration suites refuse an image the manifest does not list. The first four engines went from 4 to 9 verified image-versions (PostgreSQL 14–17, MySQL 8.4, MongoDB 7.0, SQL Server 2019/2022/2025), and the first full run caught three versions that do not work (MySQL 9.x client-side `source` handling, PostgreSQL 18's moved `PGDATA`, SQL Server 2017's tools path) — named in the changelog rather than left as gaps. One piece intentionally remains open, below.**
    - [x] Physical-restore version pre-check: where the backup names its own version — pgBackRest `backup.info`, `xtrabackup_info`, a `.bak` header — the adapter should compare it to the engine it was handed and refuse with its own message instead of letting the engine fail cryptically. `docs/engine-versions.md` §5 records the requirement and points here; the mariadb adapter's error-log surfacing is a diagnostic stopgap, not the check. **Complete 2026-08-15: all four physical-restore adapters compare the version the backup itself states with the engine in the sandbox and refuse an impossible pairing up front as `invalid_request`, naming both sides — postgres (`backup.info` `db-version` vs `postgres --version`, same major), mysql (`xtrabackup_info` `server_version` vs `mysqld`, same release series), mariadb (either metadata generation vs `mariadbd`, same series), mssql (`RESTORE HEADERONLY` `SoftwareVersionMajor` vs `SERVERPROPERTY`, downgrade only — an older backup on a newer engine is the supported upgrade path and passes). Refusal only on positive evidence: unreadable metadata, an unanswerable engine, or an implausible value skips the check rather than guessing. Adapter versions moved: postgres 0.10.0, mysql 0.10.0, mariadb 0.2.0, mssql 0.8.0.**

  Architecturally hard — more than one component in a model that gives one sandbox. The route that stays inside the contract is an image carrying every binary, with the adapter starting the auxiliaries over `exec` (everything shares localhost, so `--network none` is no obstacle):
  - [ ] Milvus — needs etcd and MinIO alongside; backup spans etcd metadata and object-store segments, tied together by `milvus-backup`.
  - [ ] InfluxDB 3 Core — no backup command exists at all: the backup is a consistent copy of the object store, so what "consistent" means operationally has to be established before a drill can claim anything.
  - [ ] Apache HBase — a realistic drill wants HDFS and ZooKeeper and there is no official image; decide whether a standalone-only drill is honest enough to ship.
  - [ ] Apache Doris / StarRocks — `BACKUP SNAPSHOT` into a repository, with FE and BE components; the all-in-one image makes the sandbox tractable, and the two products have diverged enough to need a one-or-two-adapters decision.

  Recommended against:
  - [ ] Apache Greenplum — open development stopped after 7.x, new releases are closed and registration-gated, and only stale community images remain. Record the refusal so the gap in the catalog is a decision rather than an oversight.
- [ ] Evaluate hosted/managed offering (business decision, out of scope for the OSS core).

## Deliberate non-goals (all phases)

No backup engine. No built-in scheduler. No agent daemons on database hosts unless proven unavoidable. No more than one new engine per release cycle. No UI before Phase 3. Every "no" protects the quality of the core.
