# Probavi Roadmap

Order matters. Each phase has an explicit exit criterion; do not start the next phase before meeting it. The two specifications in Phase 0 are the foundation everything else depends on — rushing them is the most expensive mistake available.

## Phase 0 — Contracts before code

**Goal:** the two load-bearing specifications exist and have survived review.

- [x] Choose project name: **Probavi** (Latin: "I have proven"). Pre-checked 2026-07-30: npm, PyPI, crates.io free; zero exact-name GitHub repos; no company hits in web search.
- [x] Canonical domain: **probavi.dev registered 2026-07-31.**
- [x] Choose license and add `LICENSE`. **Decided 2026-07-31: open-core model. This repository (the core) is Apache-2.0; Phase 3 organisational features will be offered commercially, developed outside this repository. The evidence format spec and the independent verifier stay freely available forever — paywalling verification would destroy the trust proposition. Contributions: DCO.**
- [x] Write `docs/adapter-protocol.md` v0: JSON-over-stdio protocol with four operations — `probe`, `provision`, `healthcheck`, `teardown` — including full example request/response messages, error model, timeout semantics, and versioning rules. **Approved 2026-07-31 (core-mediated sandbox-verb model); normative. Frozen 2026-08-01: conformance check list in §10, machine-readable JSON Schemas in `docs/schemas/adapter/`, CI-verified against the golden files (`internal/spec`).**
- [x] Write `docs/evidence-schema.md` v0: record fields, canonical JSON serialization, hash-chain construction, ed25519 signing, verification procedure. **Approved 2026-07-31 (RFC 8785 JCS restricted to integer-only numbers); normative, current version v1 (2026-08-01, `drill.pitr_target`). Frozen 2026-08-01: machine-readable JSON Schema at `docs/schemas/evidence/record.json` covering both published versions, worked-example golden logs + committed public key, all CI-verified.**
- [x] Proof of concept (~50–100 lines Go, may be throwaway): restore a `pg_dump` file into a Docker container, wait for readiness, run one `SELECT count(*)`, tear down. Purpose: surface real-world friction (Docker API, readiness detection, cleanup on failure) before designing around imagined problems. **Done 2026-07-30, removed 2026-09-13.** It surfaced seven findings, and the reason the spike could go is that every one of them is in the shipped design rather than in a document beside it: readiness belongs to the adapter's `healthcheck` and the core owns only the wall clock; `timings` splits into provision / transfer / restore / validate, because 1.17 s of the measured 1.47 s “restore” was neither; teardown runs on its own context with its own grace budget and is idempotent; the source reaches the sandbox through a core-mediated verb rather than a handle; engine tools are pinned to strict error semantics behind the error registry (`source_corrupt` and its neighbours); sandboxes default to no network exposure with checks executed inside them; and the docker provider sweeps orphans by label. Its own README always said it would be deleted once `internal/` existed — “none of this code is production code” — and it outlived that by six weeks in a tree where everything else is gated.

**Exit criterion:** a stranger could implement an adapter from the protocol doc alone, and could verify an evidence record from the schema doc alone.

## Phase 2 — Prove the abstractions

**Goal:** demonstrate that both extension axes (engines, sandboxes) work without touching the core.

- [x] Second adapter: MySQL/MariaDB (`mysqldump` + one physical-backup source). **Test of the protocol: if the core needs changes, fix the protocol now — it is still cheap.** **Complete 2026-07-31 (`adapters/mysql`: `mysqldump` + `mysqldump_dir` logical, Percona XtraBackup physical) with zero core changes. The protocol passed its test: the dialect difference (MySQL rejects SQL-standard quoted identifiers) is absorbed declaratively by the adapter's `sql_runner` template (`ANSI_QUOTES` via `--init-command`), and the physical flow reuses the idle-sandbox pattern with an `--init-file` auth reset mirroring the postgres adapter's pg_hba trust overwrite. Both paths proven end to end against real Docker.**
- [x] Point-in-time recovery drills: "restore to yesterday 14:32" for Postgres (WAL replay via wal-g or pgBackRest). Complete 2026-08-01: `target.pitr` config (`target_time` | `target_age`), core-side resolution + per-source capability gate (protocol already specified `pitr` in v0), evidence schema v1 records the resolved target as `drill.pitr_target`, postgres adapter drives `pgbackrest --type=time --target-action=promote` and waits recovery out; end-to-end PITR drill test proves batch-B exclusion and writability.
- [x] Second sandbox provider: Kubernetes Job **or** remote host over SSH (pick based on user demand). **Maintainer picked Kubernetes Job (2026-08-01). Complete 2026-08-01: `internal/sandbox/k8s` — each sandbox is a `batch/v1` Job driven through the kubectl CLI (no client-go, matching the docker provider's no-SDK rule; shared subprocess plumbing extracted to `internal/sandbox/cli`). Cluster-side cleanup backstop the docker provider cannot offer: `activeDeadlineSeconds` + `ttlSecondsAfterFinished` kill and garbage-collect a sandbox even if the drill host dies permanently; the host-scoped orphan sweep handles the normal case. Security: no service-account token, no ports, seccomp RuntimeDefault; pod-level network isolation is the cluster's NetworkPolicy job (documented residual difference vs. docker's `--network none`). Second axis proven: the unchanged postgres adapter restores a real pg_dump into a kind cluster end to end — zero core changes, zero adapter changes. CI runs the k8s suite against kind. Addendum 2026-08-01: the docker provider is hardened for remote daemons over the CLI's native SSH transport (`DOCKER_HOST=ssh://…`) — host-scoped sweep labels make shared daemons safe, CI proves the path over a real SSH loopback; the SSH endpoint stays in the environment because sandbox params enter signed evidence (schema §8).**
- [x] Restore-duration trend data surfaced in metrics; alert-friendly derived metrics (e.g. rolling P95 restore time). **Complete 2026-08-01: no daemon (non-goal), so the trend is recomputed after every drill from the canonical history — the evidence log itself. `probavi_restore_duration_rolling_seconds{quantile="0.5"|"0.95"|"1"}` (nearest-rank over the last 100 completed restores of the drill) plus `probavi_restore_trend_samples`, rendered into the same node_exporter textfile; README documents the two alert rules that cover staleness and RTO drift. Zero new config keys, zero evidence changes.**
- [x] Adapter developer guide + conformance test suite (`probavi adapter conformance <cmd>`), so third parties can build adapters confidently. **Complete 2026-08-01: the §10 check list is frozen in `docs/adapter-protocol.md` (15 checks: framing discipline, handshake, error-registry mapping, timing plausibility, teardown idempotence, SIGTERM handling) and implemented in `internal/conformance` — a deliberately independent second implementation of the protocol driving a simulated sandbox, no container runtime needed. Suite tests prove every check fails against 15 scripted violation modes of a fake adapter and passes 15/15 against both in-repo adapters (which the suite immediately improved: their handshake now returns the §3.1-mandated `detail.supported`). Guide: `docs/adapter-development.md`.**

**Exit criterion:** adding engine #3 requires zero core changes; an externally-authored adapter passes conformance.

## Phase 3 — The differentiating layer

**Goal:** turn verified runs into organisational trust.

**Open-core boundary (decided 2026-07-31, restated 2026-08-04):** proving that backups restore stays free forever — the CLI, adapters, sandbox providers, checks, evidence chain, `evidence verify`, metrics, notifications, and **DR game-days**, all Apache-2.0 in this repository. The line is not drawn at scale: a game-day is multi-database, dependency-ordered orchestration and is a full free feature, because proving that a whole service comes back is the product, not a tier of it. (The original wording said "proving a single drill stays free" — written before game-days existed, and it read as if orchestration were the upsell.) The organisational layer below — fleet dashboard, audit report export, RTO/RPO objectives and trends, SSO/RBAC — will be offered commercially, built on top of this open core and documented transparently when Phase 3 starts. The evidence spec and the independent verifier are never commercial.

Built commercially, **outside this repository** — listed here so the boundary is legible, not as work planned in this tree:

- Fleet dashboard (read-only web UI over the evidence store): estate-wide recoverability status, trends, drill calendar.
- Audit report export (HTML/PDF): "in the last 90 days, N drills across M databases, success rate, measured RTO distribution" — mapped to DORA / NIS2 / NIST expectations (see AGENTS.md §Compliance).
- RTO/RPO objectives in config; automatic breach detection and trend-based early warning ("restore time will exceed your RTO within ~6 months at current growth").

Work planned in this repository:
- [x] Publish the evidence format as a standalone versioned spec with an independent verifier tool. **Complete 2026-08-02 (`spec/evidence`, spec §12): the format was already versioned independently of the binary and frozen, so the gap was that verification was circular — the only thing checking the hash chain and signatures was the code that wrote them. Closed with a second implementation written from `docs/evidence-schema.md` alone, in a separate Go module with zero dependencies, which means the toolchain (not discipline) forbids it importing `internal/evidence`. Ships as `go install`-able `probavi-evidence-verify` with the §9 exit codes. The worked example moved out of `internal/evidence/testdata/` to `docs/schemas/evidence/examples/` and is now a published conformance vector: the core pins that it emits exactly those bytes, the verifier pins that an implementation which has never seen the core accepts them, and neither imports the other. Both agree on both published schema versions and on tampered input, down to the failing line. Library at 100% statement coverage, gated separately in CI.**
- [x] Get evidence off the host that produced it, without a shared filesystem or credentials on every machine. **Complete 2026-08-24 (`probavi push`, `internal/push`, spec `docs/evidence-push.md`, protocol `probavi-evidence-push/1`): one outbound HTTPS request, which a host behind NAT or in a DMZ has even when it has neither of the two usual answers. The whole file goes every time — that is what removes the state, and what makes a push idempotent and self-healing, since whatever an earlier one missed the next repairs — as `application/x-ndjson` to `<--to>/<--path>`, bearer token from the environment, optional HMAC in the notification's own header and scheme so one receiver verifies both. A push is a copy: the log is opened read-only, never modified or deleted, no flag offers otherwise, and a delivery failure (exit 2) never changes what a drill proved. Free like everything that proves and verifies restores, and deliberately receiver-agnostic: the core defines, endorses and requires no receiver, and because the bytes on the wire are the log itself, whoever holds them verifies with the public key the operator publishes — a delivery proves nothing on its own.**

**Exit criterion:** a compliance officer can hand an Probavi report to an auditor without editing it.

## Phase 4 — Ecosystem

- [x] Generated capabilities manifest for downstream consumers. **Complete 2026-08-03 (`docs/capabilities.json`, `probavi-capabilities/1`, spec `docs/capabilities.md`, schema `docs/schemas/capabilities/capabilities.json`): unplanned, and worth doing before the first announcement — the website consumes this repository as a submodule under the rule "never state a capability that is not in `docs/capabilities.json`", and that file did not exist, so every public claim was being written from README prose. That is the exact drift the rule exists to prevent, on the one surface where an inaccurate claim damages a trust product most. Now generated from the code that implements each capability: the adapters' probe goldens, the sandbox provider descriptors, the check registry, the CLI command table, the notification constants, the embedded locale catalogs, and the frozen contract version constants — with the registries refactored so they *drive* the code rather than sitting beside it (a sandbox parameter the descriptor does not declare is rejected; a check kind the registry does not list cannot be configured; a command absent from `internal/cli` cannot be dispatched). Per-adapter `adapter.json` carries only what a probe response physically cannot, and the integration suite restores from the image it lists, so "verified against PostgreSQL 16" is a record of what CI ran, never a supported-version claim. Deterministic output with no timestamp or build metadata; a fifth CI gate regenerates and fails on any diff. The manifest also states the non-goals, so a consumer knows what must never be claimed.**
- [x] The README's engine list is generated from the manifest, not written beside it. **Complete 2026-08-26 (`internal/tools/enginetable`, `README.md`, `docs/capabilities.md` §6): the Status section named all eighteen engines, their source kinds and their release state inside one prose sentence — the last public claim in this repository still written by hand, which is the drift the manifest above was built to end. Three of the four columns already existed in the manifest. The fourth needed a new field: `since`, the release an adapter first shipped in, added within `probavi-capabilities/1` (§2 permits added fields, so no version bump) and `null` while an adapter has not been released. It dates the adapter, not the engine — MariaDB reads 0.7.0 because that is when a MariaDB drill began recording `engine: mariadb`, with the earlier mysql-adapter coverage recorded in that adapter's README — and `internal/docs` holds every value to `CHANGELOG.md`, so a release that never happened, a release that does not mention the adapter, a release later than the adapter's first appearance, and a `null` left behind by a release are each a build failure rather than a plausible string. A fifth column was considered and dropped: DB-Engines rank values, read on 2026-08-26, carry a copyright notice and no statement permitting republication, so the column became the source kinds instead — the values `source.kind` takes, which is what a reader of that table actually needs.**

- [x] Bare-host SSH sandbox provider (no container runtime on the target). - [ ] **Sandbox provider catalog.** Recorded 2026-09-04 from a survey of what else could sit behind the sandbox contract (#232). The catalog exists for the reason [the engine catalogue](docs/engine-catalog.md) does — so that a request for a provider gets a reasoned answer rather than a backlog entry — but this axis is not that one, and the difference is the first thing it has to say. **An adapter is an external process anyone can write, own and version; a sandbox provider is core Go, for the life of the project.** `cmd/probavi/run.go` resolves a provider name through a switch over concrete constructors, so "pluggable" in the README means the core never learns which runtime it got, not that a provider can live anywhere else. The three that ship measure 446, 587 and 608 lines against 895, 972 and 958 lines of unit tests, an integration suite each, and a dedicated setup block in the pull-request workflow — the cost a fourth inherits before it restores anything. Two rules follow, and they belong to this catalog rather than to the non-goals list at the foot of this file, which is closed: **at most one new sandbox provider per release cycle, and none while a shipped provider is still `experimental`** — all three are today, and the gaps that keep them there are already documented (the k8s provider has no pod-level equivalent of `--network none`; the bare-host provider has no container isolation at all). A candidate also needs the demand signal Phase 2 asked for when it picked between the second and third providers. One thing here is a precondition rather than a candidate: **there is no general provider contract document.** `docs/sandbox-bare-host.md` is one provider's design spec; the rules every provider must satisfy are spread across `docs/adapter-protocol.md` §4 (the two verbs, the 256 KiB capture cap, the resolved-path rule on `put_file`), `internal/sandbox/descriptor.go`, the `Provider` and `Sandbox` interfaces in `internal/core`, and AGENTS.md §2.2. The bare-host provider was required to be spec-first and got a spec of its own; a fourth has nothing general to write one against, so `docs/sandbox-providers.md` comes before it — **written 2026-09-20**, normative, gathering the two verbs and their caps, the containment rule and whose it is, the three cleanup mechanisms, the isolation defaults other decisions lean on, the descriptor as the only place a parameter may be declared, what a record may say about a sandbox, the three doors below restated, and what the core will not grow for a provider. Three questions are one-way doors, each to be answered before the first provider that needs it rather than during it:
  - *Where a remote provider's endpoint lives.* The evidence schema forbids connection details anywhere in a record (§8), and sandbox parameters are the one operator-supplied blob copied into a signed record verbatim and unfiltered — the redactor covers adapter-originated strings, config validation checks little more than that a provider was named, and nothing inspects a parameter value. The rule holds today because no descriptor declares an endpoint parameter: the docker daemon comes from `DOCKER_HOST`, the cluster from `KUBECONFIG`, the bare host from `PROBAVI_SSH_TARGET`, all environment-only. A provider that declared `host` or `endpoint` would compile, validate, and sign it. Most of the candidates below address a remote system by name, so each of them meets this door first: either the endpoint stays in the environment as it does for all three, or the descriptor gate learns to refuse a parameter that carries one.
  - *What a sandbox parameter proves.* `sandbox.params` records the values as written in the drill configuration, so a record states what was requested, never what ran. That is exactly right for an image or a memory cap and not obviously right for a parameter that names an isolation class, which an auditor will read as a fact about the drill. Either the core reads such a value back from the runtime and records what it observed — a schema question, so a spec change first — or a parameter of that kind is documented as configuration and nothing more, and no surface may describe it as evidence of isolation.
  - *Whether a drill may run on the host that signs its record.* Every provider today puts the restored copy of production data on a machine other than the one holding the signing key, and the bare-host provider makes a dedicated target its stated premise rather than a recommendation. A provider on the drill host itself ends both. Decide whether that co-residency is acceptable, and under what premise, before any local provider — not after one exists.
  Fits the current model — reuses machinery that already ships, no new lifecycle code:
  - [ ] Sandboxed-kernel runtimes as a parameter, not a provider — `runtime` (`runsc`, `kata`) on the docker descriptor, `runtimeClassName` on the k8s descriptor. The isolation moves from a shared kernel to a sandboxed kernel or a microVM, and the code is genuinely small: one declared parameter and one case in the docker provider's argument builder, one field on the k8s pod spec and the same two additions. Two costs are not small. It meets the second door above, because the value it carries is a claim about isolation. And it cannot be claimed engine-wide: the version matrix already runs 71 jobs across 28 adapters (measured 2026-09-13, and growing with every engine), gVisor's syscall surface does not suit every engine, and `docs/capabilities.md` forbids widening "verified against" into "supports" — so the shipping unit is the parameter plus a measured per-engine table, never a blanket statement.
  - [x] Podman — first, though, the claim this repository already makes: the Arch optional dependency and the Debian suggestion both say podman satisfies the docker provider, and nothing verifies either, which is a capability claim living outside the manifest. Settle that before designing anything (#233). If the `podman-docker` shim passes the docker integration suite, a separate provider may be unnecessary and the docker descriptor's `verified_against` says so; if it does not, what fails is the specification for what a real provider must do. Either way the answer is a provider id of its own rather than a `binary` parameter on the docker descriptor: the id enters every signed record and must name the runtime that actually ran. Measured, not assumed, in either direction: rootless `--memory` needs cgroup v2 delegation or the cap is silently absent while the record shows it set, an orphan sweep cannot see containers across the rootless boundary, and `podman cp` ownership under a uid map is the `put_file` question the mssql adapter already made the core answer once. **Measured 2026-09-04 and settled without a new provider (#233):** the shim carries the provider. The lifecycle, the orphan sweep and both resource caps pass against rootless podman 4.9.3 on cgroup v2 with the systemd cgroup manager — `memory` and `cpus` reach the container's cgroup exactly as under docker, which was the open question, because a cap the runtime accepted and dropped would leave a signed record stating a limit that never held. So the docker descriptor's `verified_against` states it, `.github/workflows/podman.yml` re-earns it on the paths that can invalidate it and weekly, and the packaging lines are backed by the manifest like every other claim. One measured difference was a defect on our side rather than podman's: the sweep read `No such object` case-sensitively, so podman's lower-case refusal for a container that vanished between list and inspect fell through to the error path — at drill start, where it fails the drill. Both that check and teardown's are case-insensitive now. What is verified is the provider and not every engine: adapters run under docker only, and the descriptor says so rather than letting "verified against" widen into "supports". What stays open is the second door above, sharpened by this result rather than answered by it: an operator running podman through the shim gets records that read `provider: docker`, because the id names the code path and not the runtime that answered it — the same way a remote daemon over SSH already does. A separate provider id is one answer and recording the observed runtime is another, and neither is worth taking before that door is.
  Needs a decision before code — a door above, or a demand signal this catalog does not have:
  - [ ] Local systemd provider (`localhost`) — the bare-host design with the SSH hop removed, for machines that run the binary but allow no container runtime. The code is not the obstacle: the provider is transport-agnostic apart from one method, and the slice, workspace, marker-sweep and deadline-timer machinery carries over. The third door above is.
  - [ ] `systemd-nspawn` — an ephemeral filesystem snapshot and a private network namespace would close the residual gap the bare-host spec documents. But nspawn is a container runtime, so it does not serve the premise that motivates the entry above it, and it needs its own audience before it needs a design.
  - [ ] Incus / LXD — system containers and virtual machines behind one CLI, ephemeral instances, network denial by profile: a clean fit for the contract, and one no user has asked for.
  - [ ] HashiCorp Nomad batch jobs — the Kubernetes Job analogue for estates that run Nomad. The lifecycle maps; the friction is `put_file`, where there is no `cp` and the bytes would go over `exec` stdin. That shape already exists — the k8s provider transfers files exactly that way rather than through `kubectl cp` — so what needs measuring is whether `nomad alloc exec` sustains a multi-gigabyte stream at all, and what the protocol's capture cap does on that path.
  Recommended against:
  - VM lifecycle around the bare-host provider — Proxmox, libvirt, ephemeral cloud instances. Refused as a provider and documented as a wrapper instead, because it already is one: the target is an environment variable, so cloning a template, exporting the target, running the drill and destroying the machine is a shell script with no core code in it. What would need core code is the part that makes it a provider — a hypervisor-side sweep of tagged machines running when no drill is — and that is the daemon the non-goals close. The measurement worry that usually accompanies this idea does not apply: sandbox creation is timed as `provision` and never as `restore`, a split that exists because the proof of concept measured 1.17 s of a 1.47 s "restore" as container startup.
  - Cloud container jobs — ECS/Fargate, Cloud Run Jobs, ACI, Fly Machines. A drill reads its backup from the local filesystem with no network, so these are compelling only for operators whose backups are already in that cloud, which is the object-storage question left open in the engine catalog below rather than a sandbox question. Recorded as out of scope until that one is answered.

## Depth: what a drill proves

The phases above are about reach — more engines, more sandbox providers, more of the loop. The items here are about depth: the same drill, proving more than it proves today. They sit outside the phase order deliberately, because that order answers *what exists yet*, and every one of these rests on something that already ships.

- [ ] **Backup manifest.** A record already carries the checksum, size and creation time the adapter measured on the source; nothing carries what those values were meant to be, so a drill proves that the file it was handed restores rather than that the file the backup tool wrote restores. An optional `source.manifest` names a JSON file written at backup time — `expected_checksum`, `expected_size`, `created_at`, `engine_version` — and the core compares before the bytes move, refusing with `source_corrupt` on a mismatch. Deliberately limited to what is checkable before transfer: expected row and table counts need a live query against the restored database and belong to the baseline check. **The specification has to state what this does not prove.** A manifest lying beside the backup catches corruption, not tampering, because whoever can rewrite one can rewrite the other. The tamper-evident form is a different design: an expected checksum written into the drill config is covered by `drill.config_hash`, which is signed — and does not scale to one config per backup. Open, not settled by this line: whether a `probavi manifest write` helper ships at all, or the JSON shape is documented and `sha256sum` produces it. A helper would be the first thing asking for Probavi on the host where backups are taken — a one-shot command rather than the daemon the non-goals refuse, but worth naming before it is built. New config key and new evidence fields: spec first (`docs/backup-manifest.md`, JSON Schema), then code. Exit: a backup altered between the backup run and the drill fails before restore, and the record names the value that disagreed.
- [x] **Which backup a `*_dir` kind picks.** Done 2026-09-25 (started 2026-09-24). `source.params.select` takes `newest` (the default, and what every drill written before it existed does), `oldest` or `random`, on every kind in the catalogue that chooses a backup out of a directory — **35 kinds across 26 adapters**, each with its own `selection.go`: `postgres` 0.18.0, `mysql` 0.15.0, `mariadb` 0.5.0, `etcd` 0.5.0, `mongodb` 0.6.0, `sqlite` 0.2.0, `duckdb` 0.2.0, `cassandra` 0.5.0, `scylladb` 0.3.0, `prometheus` 0.6.0, `victoriametrics` 0.3.0, `weaviate` 0.2.0, `solr` 0.7.0, `mssql` 0.9.0, `arangodb` 0.2.0, `influxdb` 0.5.0, `redis` 0.6.0, `valkey` 0.5.0, `clickhouse` 0.4.0, `couchdb` 0.2.0, `firebird` 0.2.0, `neo4j` 0.2.0, `h2` 0.2.0, `qdrant` 0.2.0, `questdb` 0.2.0, `tdengine` 0.5.0. It cost no core config key, no adapter protocol version and no evidence schema change: params is what the core hands an adapter uninterpreted, and it never reaches a record — while `backup.checksum`, `backup.size_bytes` and `backup.created_at` still name what was proved, which is what makes `random` acceptable. **The semantics, settled once and copied:** `oldest` is not `newest` inverted, because wherever an artifact can state its own instant, one that states none loses under *both* policies — datedness is not a clock, so `precedes` is written out beside `beats` in every adapter rather than derived as `!beats`, with a test that fails if they are ever folded together. `random` draws only from the artifacts that can be dated, where any can, so a directory's stray sidecar is never drawn. The parameter is refused rather than ignored on a kind that selects nothing, and on one whose config already names the member outright. **Where an artifact records no clock** — an etcd snapshot, a mongodump archive, a SQLite, DuckDB or H2 header, a Solr or QuestDB directory, a Qdrant snapshot, a couchbackup file, a gbak header carrying a zoneless wall clock, a neo4j dump — the order is file time, `oldest` is only as strong as the directory's modification times, and every README says so. **Where it does** — a Cassandra or ScyllaDB `manifest.json`, a Prometheus block's `meta.json`, a VictoriaMetrics, Weaviate or ClickHouse metadata file, an InfluxDB manifest stem, an RDB `ctime`, an ArangoDB `dump.json`, a taosdump `dump_result.txt` — `oldest` is exactly as strong as `newest` already was. **Three adapters needed more than an ordering.** `weaviate` refuses a newer failed or in-progress attempt, and `clickhouse` a newer unreadable archive: both guard `newest`, where the record would otherwise imply the newest, and neither applies under `oldest` or `random`, where the operator has named which end of the window the drill is about — otherwise one broken backup job would make that far end undrillable, which is the only thing `oldest` exists to reach. `mssql` selects in two places: `bak_dir` and `bak_with_logins` rank artifacts in the sandbox over what `RESTORE HEADERONLY` reported, where the datedness rule survives inversion, and `bak_chain` picks which full a chain is *anchored* on by the engine's own checkpoint LSN, where it does not survive because a full with an unreadable checkpoint is refused rather than ranked — so `oldest` on a chain directory proves that the far end of the window still replays forward through its own differentials and logs, the strongest form this feature takes. **One ordering was corrected rather than extended:** `tdengine` used to substitute a directory's modification time for a missing recorded instant and compare the two against each other, so a dump freshly copied in and recording nothing could outrank the genuinely newest dump; the two clocks are now kept apart, which changes what `newest` picks in a directory that mixes them. `aerospike`'s `asbackup_dir` takes no policy and never will: `asbackup -d` splits one backup across the files of one directory, so the directory *is* the artifact and there is no member to choose. Not included: `all-within: <duration>`, which is not a selection policy but several drills wearing one — it breaks one drill / one record and the single wall-clock deadline, and cron or a game-day already runs several drills. Still open, and deliberately: promoting `select` to a validated `target.source` key now that the semantics have settled across the catalogue; that order was the reversible one. Exit met: a drill can prove the oldest backup in the retention window, and the record says which one it proved.
- [x] **Refuse a chain with a hole in it, before moving any bytes.** **Complete 2026-09-23 (`adapters/postgres` 0.16.0, `chain.go`).** `adapters/mssql` already refused a log-sequence gap; pgBackRest is the other shipped source with a chain, and it now refuses one too — the ancestor chain through `backup-prior`, the chosen backup's own archive endpoints, and a point in time no backup finished before. Measured first, against pgbackrest 2.59.1: with the stop segment removed `pgbackrest restore` exits 0 and the drill failed only at server start, as `restored cluster failed to start: pg_ctl: could not start server`, after the repository had been copied into the sandbox — an integration test now asserts the sandbox is empty when the refusal comes. Three limits are written into the README rather than discovered: only the chosen backup's own WAL range (deleting the full's segment was measured to leave a differential restore working), only its endpoints (a repository records no WAL segment size), and a repository this code cannot read is not judged. Still open for the other chains: binlogs, once that PITR lands.
- [ ] **wal-g and Barman sources on `adapters/postgres`, with PITR.** Half done: **Barman complete 2026-09-23** (`adapters/postgres` 0.17.0, source kind `barman`, `barman.go`). The point-in-time item in Phase 2 promised WAL replay via wal-g *or* pgBackRest and shipped only the second; `barman` is the second source kind in this repository to declare `pitr`, out of roughly a hundred. Barman's own restore is server-side and does not fit a drill, but its layout does — the adapter places `base/<id>/data`, points `restore_command` at the `wals/` tree and lets PostgreSQL recover — and, measured, **it needs nothing the official postgres image does not already ship**, unlike the `pgbackrest` kind. Refused before the transfer the same way, plus one refusal in Barman's own vocabulary: `WAITING_FOR_WALS` is not a backup a drill can prove. **wal-g remains**, and is deliberately a separate piece of work: it has no distribution package, so a verified image means a pinned release binary, and its home is object storage — only its filesystem backend can serve a sandbox that starts with no network, and the rest waits on the object-storage door.
- [ ] **Binlog PITR on the physical fulls — `adapters/mysql` first, `adapters/mariadb` after it.** A physical full leaves `xtrabackup_binlog_info` naming the log file and position at the instant it was taken, and replaying from there to the target is the rest. Same cost profile as the item above: the `pitr` gate has been in the protocol since v0 and both adapters already have their physical source kind, so this is adapter work with no core change, no protocol version and no schema bump. Two entries rather than one on purpose — MySQL and MariaDB are separate adapters here, with separate tools and separate binlog semantics, and one line would hide two measurement days and two adapter versions. One honesty point for the adapter READMEs: binlog event timestamps are second-granular while a drill's target is an absolute instant in milliseconds, so the point actually reached can be coarser than the point requested. The schema is already right about this — `drill.pitr_target` records the instant *requested* — but a reader who is not told will assume otherwise. Where the logs live is a `source.params` value, following the selection decision above, because binlogs sit in a server's data directory or an archive rather than beside the backup. The chain pre-check above is what catches the gap this path fails on.
- [ ] **Encrypted backups, without a new core key.** A backup that cannot be decrypted is not a backup, and nothing in the documentation says how to drill one. What that needs is smaller than it looks. `source.credential_env` is already defined as the names of the environment variables an adapter needs *in order to read the backup*, which is the decryption key exactly; adapters already use it for engine passwords. So an encrypted source is an adapter-side source kind on the existing mechanism — no core config key, no protocol change, and no adapter obliged to care. What ships first is the cheaper half: the staging pattern for encrypted backups in `docs/backup-staging.md`, where moving the bytes to the drill host already lives, with the boundary stated in its §8. A `source.decrypt` key that runs a command is deliberately not the shape: it is code execution driven from the file whose bytes `drill.config_hash` signs, for a job the same cron entry already does. One warning for the in-sandbox route, recently paid for: #327 was an adapter assuming a tool the engine's image did not ship, and blaming the backup for its absence — assuming `age` or `gpg` across thirty-two images is that trap again. Note also that the failure this is aimed at, a rotated key, is caught more cheaply by drilling the `oldest` member above. Exit: drilling an encrypted backup is a documented path rather than a guess, and no key material can reach a record.
- [ ] **Checks the adapter declares, rather than checks the core composes.** `internal/checks` builds `SELECT count(*) …` and `SELECT max(…) …` as text and hands it to the adapter's `sql_runner`. Four built-ins written that way have produced four engine-specific failures across thirty-two engines — TDengine refusing SQL-standard quoted identifiers (#276) and `max()` over a timestamp (#293), Cassandra refusing the `WHERE 1=0` probe as not-CQL (#277), QuestDB's CRLF surviving inside a quoted value (#275) — with two more on the output side of custom checks (#175, #274). That rate belongs to the model rather than to bad luck: the core writes SQL for engines that have none, or have their own. The shape that scales is the inverse — the adapter declares the statement for a named check in its `probe` response, and the core runs what it is given. That is a `probe` field, so it is an adapter-protocol change: spec first, version bump, conformance check. What it would then allow, in demand order and not as a commitment: `table_count`, and `index_exists` for the failure mode worth naming — a logical restore that exits 0 having dropped every index. `role_exists` and `schema_exists` wait for someone to ask, because both concepts are absent from two thirds of the catalogue. Exit: a structural assertion is written once per engine by the adapter that knows the dialect, never once in the core for all of them.
- [ ] **Baseline reconciliation**, after the manifest and the mechanism below it, not before either. A `baseline` check compares aggregates of the restored data — row counts, `max(<primary key>)`, `sum(<column>)` over named tables — against the expectations a manifest recorded, and carries the expected table and row counts that the manifest item deliberately does not. What it adds over `row_count` is the sharper half of the same question: `row_count` measures against a bound written by hand, so a restore that lands ninety per cent of the rows passes a loose one, while a recorded expectation does not. That is the failure class three engines in a row have shown — a restore tool exiting 0 having restored part of the data. Two dependencies, both real: the manifest, for something to compare against, and adapter-declared statements, because `max(pk)` and `sum(column)` are SQL concepts and would otherwise reproduce the failures listed above one level up. A per-table tolerance is a question for the specification rather than a number for this plan: an expectation taken from the backup itself needs none, and one taken from the live database after the backup finished needs one — a dial that tunes a proof into an opinion, and it has to be argued for where it is defined. Exit: an unexplained delta fails a check and the record names it, in aggregate only (evidence schema §8).
- [ ] **An `integrity` check**, on the mechanism above, and different in kind from the structural assertions that share it. Those state that something is present; this runs the engine's own corruption detector — `amcheck` or `pg_checksums`, `CHECKSUM TABLE`, `db.collection.validate()`, `DBCC CHECKDB`, `PRAGMA integrity_check` — and it is the only instrument here that catches damage the backup copied faithfully, because the damage was already in the source. Three things this costs, none of them visible from the list of tool names. The SQLite precedent is not a head start: `PRAGMA integrity_check` already runs in that adapter, but as part of the restore verdict rather than as a check a drill configures. Five engines of thirty-two have an instrument of this kind at all. And the ones that do are not free — `pg_checksums` wants the cluster down and checksums enabled, `amcheck` is an extension that has to be in the dump, and `DBCC CHECKDB` on a large database can consume the drill's whole wall-clock budget, which is hard. So this arrives per engine, after a measurement day, the way every adapter did. Exit: silent page corruption carried faithfully inside a physical backup fails the drill instead of restoring cleanly.
- [ ] **The age of the restored data, as a measured fact.** A record states that a backup restored and how long it took; it does not state *which moment the restored data corresponds to*. `backup.created_at` is the backup's claim about itself rather than a measurement of what is inside it, and `drill.pitr_target` answers the question only for the drills that asked for a point in time. So a record can say "restored cleanly" while leaving out the thing an auditor asks first: how much data a recovery from it would have lost. Measure the newest data in the restored copy against the drill's own clock and record the difference. Three constraints hold this honest. It is measured on the restored data or it is `null` — a manifest's `created_at` is the backup's self-report and must never populate it, and the schema already requires unavailable values to be null rather than absent. Reading the newest value means a statement in the engine's own dialect, so this rides on adapter-declared statements above rather than beside them (#293 is exactly an engine refusing `max()` over a timestamp). And the field is named for the fact it carries, not for an objective: RPO is a target, and naming a measurement after a target is the same category error as calling a measured restore duration an RTO. The objective itself, and breach detection over it, stay on the commercial side of the boundary above — what this adds is the signed number they would both be computed from. Evidence v3, in the single bump below. Exit: a record states the data-loss gap it proves, not only the restore time.
- [ ] **What the sandbox actually was, not only what was asked of it.** The catalogue above already states the gap in its own words: `sandbox.params` records the values as written in the drill configuration, so a record says what was requested and never what ran. Two facts close it. The engine image's digest is the stronger one and completes a set v2 began: `adapter.digest` and `env.probavi_digest` exist because a version is a claim a build makes about itself, and a record can therefore say which bytes wrote it and which adapter ran — while `sandbox.params.image` holds `postgres:16`, a tag, which points at different bytes over time. Nothing today identifies the engine that performed the restore. Null where there is no image, as on a bare host. The applied memory and CPU are the weaker half and have to be worded for what they are: what the provider applied, null where a provider cannot answer — a docker host config states a limit, a Kubernetes Job without one takes what the node has, a transient systemd scope carries `MemoryMax`. Without them a duration in the record is a number with no scale beside it. This asks providers a question they are not asked today, so it edits the provider contract in `docs/sandbox-providers.md`, which is normative: spec first. Evidence v3, in the single bump below.
- [ ] **Whether the host believed its clock.** Nearly everything a record asserts rests on the host clock: `ts`, `backup.created_at`, `drill.pitr_target`, and every duration. A log whose whole value is *this happened on this date* rests that value on a fact it never attests. An `env.clock` field, read from `timedatectl` or `chronyc` where either answers, records it cheaply — and has to say what it attests, in the manner `adapter.digest` already narrows its own claim in the schema. A synchronised flag records that the host **believed** it was synchronised; a lying or manipulated time source produces the same answer, so the field carries a belief and not a time. Null is the ordinary outcome outside systemd, which the schema's own convention already covers. Place it correctly against the witness item below: an external timestamp is evidence of time because someone other than the host asserts it, while this is the cheap partial version of the same property. They complement each other, and this one must never be described as doing the other's work. Evidence v3, in the single bump below.
- [ ] **One `probavi-evidence/3`, carrying everything above that needs a field.** The items in this section ask for new record fields four times over, and each bump costs the same set: the specification, the JSON Schema, a byte-exact golden `log_v3.jsonl`, support in the independent verifier that shares no code with the writer, and a test pinning the supported versions in both directions. Paying that once is discipline; paying it four times is waste. The fields, all nullable, all from accepted items above: `backup.expected_checksum`, `backup.expected_size_bytes` and `backup.manifest_hash` (which pins the manifest the way `drill.config_hash` pins the configuration), the age of the restored data, `sandbox.resources{memory,cpus}`, `sandbox.image_digest` and `env.clock`. Spec, schema, vectors and verifier before code, exactly as §11 and §11.2 did it. Deliberately not included: a `timings_ms.fetch` phase. The core downloads nothing today, and whether it ever will is the open object-storage door in the catalogue above, not a settled plan — a fixed-shape schema would carry that field as null in every record forever if the door stays shut. If it opens, the phase is part of that decision and gets its own bump.
- [ ] **An outside witness for the chain head.** The chain and the signature defend against everyone who does not hold the signing key. They do not defend against whoever does: that party can rebuild the whole log with any content and re-sign it from the first record, and the result is internally consistent, because nothing in the format dates it. The threat model names the attacker who wants to forge *everything was fine*, and this is the half of that attacker the local key cannot reach. An external timestamp closes it for everything before the timestamp: a receipt over the head at a moment proves the log held that content then, and a later rewrite produces a different head. Three things make this fit unusually well. The primitive already exists — §9.1 defines the head as `<seq>:sha256:<hex>` and requires every verifier to report it on every run. It costs no schema version: §9.1 states that an anchor is an input to verification and never part of the format, no byte changes and the version does not move, and a receipt is an input of the same kind. And keeping the receipt beside the log rather than inside it is what the anchor decision already settled. Two things the specification has to say plainly. A private RFC 3161 authority and a public transparency log are not interchangeable: the first sees a hash and nothing else, while publishing to the second also publishes that this organisation runs drills and how often — which not every self-hosted user wants known. And the shape is a CLI driven from outside, not a library pulled in, for the same reason the sandbox providers drive one. Because a verifier prints the head today, anchoring is already a shell line; so the documented path comes first, and the code is the part that genuinely needs code — `--witness` in both verifiers. Getting anchoring *used* rather than merely available is part of this item and not a separate one: a worked example is what makes an optional flag routine, and pushing a head to a git remote from inside the core would add a dependency and an egress path for what one cron line already does. Exit: a log re-signed after the fact with the operator's own key is detectable by anyone holding the receipt.
  Recommended against — the refusal is recorded so that a request gets an answer rather than a second discussion:
  - A `query_latency` check, running a named read query and failing above a millisecond threshold. What it measures is a query in the sandbox: cold caches, the memory and CPU the drill allocated, on whatever host happened to run it. An absolute threshold there cannot separate *the index is missing* from *the runner was busy*, and the failure it is aimed at — indexes lost in a logical restore — has a deterministic instrument in `index_exists` above. The deciding argument is the output: a flaky check here is not a red run somebody re-runs, it is a false `fail` signed into an append-only log that can never be corrected. A check known to be wrong sometimes subtracts from the one property the log exists to have. What is answerable today already is: `service_healthy` plus a custom `sql` check proves the query answers over the restored data.
  - A `max_duration` check, failing a drill when a phase runs past a configured limit. The boundary above already names this one on the commercial side — objectives in the configuration, and breach detection — so it is not a decision this line makes. What is worth writing down is why withholding it costs an auditor nothing: `timings_ms.restore` is measured by the core and signed into the record, so anyone holding the log and their own objective can compare the two without a licence, without the hub, and without trusting this project's arithmetic. Nothing provable moves behind a wall; only the comparison does. The counter-argument — that a verdict belongs in the signed record rather than in a Prometheus rule — is answered the same way: the measured duration is a fact and is signed, while a threshold is an intention, and signing an intention makes nothing more provable. The alert rule that renders the verdict today is in the README.
  - A `hook` check running a user-supplied container image beside the sandbox, its exit code the verdict, to smoke-test an application against the restored data. The aim is sound — a restore that satisfies row counts and breaks the application is a false green — and the route collides with five things at once. A check is defined as a validation written in whatever language the engine answers to, and an arbitrary image is not that; widening the word is its own decision. Placing a second container on the sandbox's network is provider-specific knowledge — a docker network, a Kubernetes NetworkPolicy and a second pod, nothing at all on a bare host — and the core holds no provider-specific logic by rule. The Oracle precedent cited for it says the opposite: that adapter creates no network, it checks whether the sandbox it was given is on an internal one and refuses with instructions if not, so the operator builds it and passes it as a parameter. A second component in a model that grants one sandbox is the definition of the architecturally-hard group in the catalogue above, where engines wait for exactly this reason. And the result would be poor evidence: with stdout correctly excluded by §8, a failed hook carries an exit code and no detail, which records that something broke and nothing about what. What exists for the same need: a custom `sql` check, in the engine's own language, is the definition above; and whether a whole service comes back is what a game-day is the unit for.
  - A `probavi report` command summarising a log over a window — runs, success rate, restore duration quantiles, in Markdown or HTML. Put the two sentences side by side: the boundary above describes the commercial audit-report export as *in the last 90 days, N drills across M databases, success rate, measured RTO distribution*, and the proposal is ninety days, runs, success rate and a duration distribution. They are one sentence, and the only thing the commercial side adds is the framework mapping, which belongs there for its own reasons. Calling a version of it free and minimal is not a safeguard: anything merged here is free permanently, so *minimal* describes the size of the first commit and nothing else. No proof is withheld by leaving it out — every number such a report would print is in the signed log, and `evidence verify` already returns a machine-readable result including the chain head on every run, so a holder of the log and the public key computes all of it without a licence. There is a positive reason too: the evidence format is a published specification with an independent verifier precisely so that anyone can build tools over it, in any language, without asking. A reporter is that ecosystem's natural first tool, and the core growing its own would both sit on the boundary and crowd out the people the specification was published for.
  - An `ext` object in the record: a free-form field the verifier ignores, so that future additions need no major version. Its own description is the refusal — *verifiers ignore its content but it is signed*. The schema says a record has exactly the fields listed and that any addition moves the major (§3, §10), and that is not a formality to route around: it is what makes an unexpected field a rejection rather than an extension nobody reads. The offer this project makes is that a third party holding the public key and the log can check everything the record contains; an `ext` puts signed content inside a record that no verifier ever examines and that every verifier still calls valid. The cost of a major version is the price of that property, and it is not payable in promissory notes.

**Process and CI**
- [x] Gate the one-engine-per-release rule, which three sentences state and nothing enforced. **Complete 2026-09-22 (`internal/docs`).** Two gates rather than one, because two doors are open. Counting the manifests that carry `since: null` — already this repository's spelling of *shipped in no release yet*, held in both directions by the gate beside it — catches a second adapter before it ships, with no git history, no tag lookup and nothing to diff. And no release from 0.8.0 onward may be named by more than one adapter's `since`, which closes the route the first cannot see: a pull request that adds an adapter *and* dates the changelog carries a `since` naming that new release and is never null at all. The floor is 0.8.0 because 0.1.0, 0.2.0 and 0.7.0 each shipped more than one and `since` records what happened rather than what the rule would have preferred; the twenty-five releases since have shipped exactly one apiece. Adapter ids are the unit, which is the honest one: PostGIS, pgvector, TimescaleDB and Percona arrived as `verified` entries and spend nothing, while MariaDB took an id and spent it, because a record names what restored by `adapter.name`.
- [x] Run the released artifacts, not only the source tree. **Complete 2026-09-22 (`packaging/drill-from-archives.sh`).** The archives a release publishes are unpacked in a musl container holding nothing but the docker CLI, checked against the release's own `SHA256SUMS`, asserted to have no toolchain beside them, and asked to complete a real drill — a live `pg_dump` restored into a real sandbox, `service_healthy` and `row_count`, then the log verified offline by the same released binary. The release workflow runs it over its own `dist/` before it drafts anything; CI runs it on every pull request on amd64 and arm64, natively. What only this can prove is the build identity: the archives carry flags no other build uses, and the `-X main.version` that stamps `env.probavi_version` into every signed record is silent when the symbol moves — so the version is read back twice, from `probavi version` and from the record itself, and an unstamped build fails the gate. Writing it found a second thing. `docker run` without `-i` leaves the container's stdin empty, so a heredoc fed to `sh -eus` runs nothing and exits 0: the three CI steps that install the `.deb`, `.rpm` and `.apk` into Debian, Fedora and Alpine had been green without executing a command since 2026-08-05. Both are now gated — the drill has to run before the draft, and no workflow may feed a heredoc to a shell reading stdin without `-i`.
- [x] Move the engine catalog into `docs/engine-catalog.md`. **Complete 2026-09-23.** It was 109 KB of this file's 184; what is left reads as a plan at 77 KB. Every entry travelled unchanged — 52 checkbox lines in, 52 out — and the four group paragraphs became headings; `docs/engine-licensing.md` and `docs/backup-staging.md` now point at the catalogue rather than at a file that no longer holds it. The sandbox-provider catalogue stayed: it is a tenth the size and carries cadence rules a plan wants nearby.
- [x] Say where the translations came from, where the translations are read. **Complete 2026-09-23.** The notice every translation already carries now states it: made inside this project, passed the review `docs/i18n.md` §5 requires, read natively only where a maintainer reads that language — Hungarian today — and how to send a correction. Uniform across the four translated READMEs and, for the twenty-three catalogues, in the Localization section of `README.md`, because a catalogue is a flat JSON map with nowhere to put a note. An `i18n-native-review` pin is the machine-readable half and is gated, so the claim cannot vanish from one file unnoticed. No draft label and no gate on reviews arriving, for the reasons §7.2 now records.

## Deliberate non-goals (all phases)

No backup engine. No built-in scheduler (cron/systemd-timer + lock file + timeout is the way). No daemon on database hosts. No web interface. No secrets management beyond reading credentials from env/file for the duration of one drill or one push. No telemetry and no phone-home. No more than one new engine per release cycle.

The list is closed, and none of it is qualified with "yet", "unless proven unavoidable" or "before Phase 3": a non-goal with an escape clause is a roadmap item. `AGENTS.md` §2.4 carries the same list. `docs/capabilities.json` carries the six that describe the software; the engine rate limit is a release-cadence rule rather than a capability, so it has no entry there.

Every "no" protects the quality of the core.
