# Probavi internationalization (i18n)

This document is normative for how Probavi localizes user-facing CLI
output: the catalog format, the locale selection rules, the translation
boundary, and the gates that keep catalogs honest. English is the
canonical source language of the project and the fallback for
everything, always (AGENTS.md §5.7).

Status: foundation implemented 2026-08-02; the shipped languages and
the per-language rollout are tracked in ROADMAP.md Phase 4.

---

## 1. The translation boundary

**Translatable** — prose written for a human reading the terminal:

- the `probavi` usage/help text,
- CLI diagnostics on stderr ("--config is required", "unknown command",
  …),
- configuration-validation diagnostics from `internal/config` (drill and
  game-day files): the translator is injected into `Load`/`LoadGameDay`,
  so `probavi run --config broken.yaml` explains the problem in the
  operator's language. Config-key locators (`checks[0]`,
  `notify.webhooks[1]`) and the config keys themselves stay verbatim —
  they are the vocabulary of the file being fixed.

**Never translated** — machine contracts and operational surfaces, in
any language, ever:

- evidence records and everything inside them (schema §8 vocabulary,
  error codes, check names, details),
- the one-line JSON summaries of `probavi run` / `probavi gameday` and
  the JSON outputs of `evidence verify`, `evidence keygen`,
  `adapter probe`, `adapter conformance` (field names *and* values,
  including `skip_reason` strings pinned by docs/gameday.md),
- the adapter protocol, notification payloads, and config file keys,
- structured logs (slog): logs are grepped, shipped, and alerted on —
  translating them would break every runbook,
- conformance verdict tokens (`ok` / `FAIL`) on stderr: they mirror the
  JSON report vocabulary.

Not yet covered: flag descriptions and the Go flag package's own parse
errors, plus diagnostics produced inside YAML unmarshaling (durations,
scalar types, syntax annotations) — they have no path to a translator.
Wrapper lines of the form `probavi run: %v` are locator prefixes, not
prose, and stay as they are; errors raised by other internal packages
(evidence, adapters, sandboxes) remain English operational output.

## 2. Locale selection

The locale is resolved **once, in `main()`**, from the environment —
POSIX order with a Probavi-specific override, no CLI flag, no config
key:

```
PROBAVI_LANG  →  LC_ALL  →  LC_MESSAGES  →  LANG
```

The first non-empty value wins. Values are normalized like locale
strings: case-insensitive, codeset and modifier stripped
(`hu_HU.UTF-8` → `hu`), `C` and `POSIX` mean English. An unknown or
malformed value falls back to English silently — a wrong `LANG` must
never break a cron drill. Tests construct the translator explicitly, so
suites are deterministic regardless of the machine's environment.

## 3. Catalog format

One embedded JSON file per language under `internal/i18n/locales/`,
named `<tag>.json` (lowercase ISO 639-1):

```json
{
  "probavi run: --config is required": "probavi run: a --config megadása kötelező"
}
```

- **The key is the English text itself** (gettext convention), verbatim
  including format verbs and trailing newlines. A missing key means the
  English original is printed — fallback is structural, not a special
  case.
- Format verbs (`%s`, `%q`, `%d`, `%v`, …) must appear in the
  translation in the same order with the same verbs; translations may
  not add, drop, or reorder them.
- Catalogs are compiled into the binary via `go:embed`: a single static
  binary stays a single static binary, and a catalog cannot be swapped
  or corrupted at run time.

## 4. Gates (CI-enforced)

The message set is defined explicitly — `cmd/probavi/messages.go` for
the CLI surface plus each emitting package's own registry
(`internal/config/messages.go`, exported as `config.Messages()`); the
cmd test suite gates their union. Per locale, tests enforce:

1. **Completeness** — every message has a translation (a new user-facing
   string cannot ship untranslated for an already-supported language),
2. **No stale keys** — every catalog key is in the message list
   (translations cannot outlive their source text),
3. **Format-verb parity** — as defined in §3,
4. every embedded catalog parses.

A language is "supported" when its catalog exists and passes these
gates; partially translated languages do not ship. The gates are the
i18n analog of the schema golden tests: they keep human-language output
as honest as the machine contracts.

## 5. Adding a language

1. Copy an existing catalog under `internal/i18n/locales/<tag>.json` and
   translate every value (a linguistic review pass is required before
   merge; native-speaker feedback is welcome and folded in as it
   arrives).
2. Run the test suite — the §4 gates must pass.
3. Tick the language in ROADMAP.md Phase 4.

No Go code changes are needed: the embedded directory is the registry.

## 6. Language policy

English is the default and the canonical source; translations are
derived artifacts. The supported-language roadmap (ROADMAP.md Phase 4,
decided 2026-08-02) is Hungarian first, then the official languages of
the EU in native-speaker order. Contributions for further languages are
welcome under the same gates.

Catalogs have the same provenance as the README translations and it is
stated in the same terms: made inside this project, reviewed as §5
requires, and read natively only where a maintainer reads that language —
Hungarian today. A catalog is a flat JSON map (§3) with nowhere to put a
note, so the statement lives where the language list is read: the
Localization section of `README.md`.

## 7. Translated documentation

Decided 2026-08-04. Documentation translation is deliberately narrow:
**only marked spans of `README.md`**, and nothing else in the
repository. The specs in `docs/` are normative and stay English-only —
a normative document that exists in several languages has several
possible readings, which is the last thing an evidence format needs.
`AGENTS.md`, `ROADMAP.md`, `CHANGELOG.md`, and the adapter READMEs are
contributor and operator surfaces that follow the same rule.

Long-form translated material for non-English audiences belongs on the
website, which consumes this repository as a submodule and must obey
the capability rule of AGENTS.md §5.8 regardless of language.

### 7.1 Marked spans

The English README marks the translatable spans inline:

```
<!-- i18n:intro:start -->
…
<!-- i18n:intro:end -->
```

A span name is lowercase `[a-z0-9-]+`; spans may not nest or repeat.
Marked spans hold the **stable** prose — what Probavi is, why it
exists, the non-goals. Anything version-bearing (`## Status`), any
command example, and any capability inventory stays outside the
markers: those change with nearly every release, and a translated copy
of them is a claim nobody can keep current. `docs/capabilities.json`
remains the only machine-readable statement of what ships.

The span content is the bytes between the two marker lines. Its hash is
the SHA-256 of those bytes with leading and trailing whitespace
trimmed, hex-encoded.

### 7.2 Translation files

One file per language at the repository root, `README.<tag>.md`, with
the same lowercase ISO 639-1 tag as the catalogs. Each file opens with
its pins:

```
<!-- i18n-source: README.md -->
<!-- i18n-span: intro sha256:<64 hex digits> -->
<!-- i18n-span: non-goals sha256:<64 hex digits> -->
<!-- i18n-native-review: yes | no -->
```

and carries, visibly, the sentence **`English is authoritative.`** — in
English, in every language, so a reader who cannot read the target
language still learns which document binds — together with the date of
the translation and a link back to the English README.

The same visible notice states **where the translation came from**: that
it was made inside this project, that it passed the review §5 requires,
whether anyone who reads the language natively has read it, and how to
send a correction. `i18n-native-review` is the machine-readable half of
that sentence, so a gate can check the claim exists while the prose
carries it to the reader. The two must agree, and the prose is what a
reader is owed — a pin nobody sees answers nobody's question.

Deliberately not a draft label, and deliberately not a gate blocking new
languages on reviews arriving. A label that says *do not trust this yet*
discourages the reader most likely to fix it, and a gate whose green
depends on an outside volunteer appearing cannot be satisfied by doing
better work, which is what every other gate in this repository asks of
the person who trips it.

### 7.3 Gates (CI-enforced)

`internal/docs` is a test-only package that holds every translation to
the English source. Per file:

1. **Currency** — every marked span is pinned and every pin matches the
   current bytes. Editing English prose inside a span fails the build
   until each translation is refreshed and its pin updated,
2. **No orphan pins** — a pinned span that the README no longer marks
   is an error,
3. **No version claims** — a release-version token (`v1.4.0`, …) in a
   translation fails: versions live in the English README and in
   `docs/capabilities.json`,
4. **Authority notice** — the English sentence above must be present,
5. **Navigability** — the language row of `README.md` links every
   committed translation, and links nothing that does not exist,
6. **Provenance** — every translation carries exactly one
   `i18n-native-review` pin, reading `yes` or `no`, so the claim in its
   notice cannot quietly go missing from one file.

This is the prose analog of the §4 catalog gates, with the same
principle behind it: a translation may exist in this repository only
while a machine can prove it is current. A translation that cannot be
kept current is deleted, not left to rot — a stale translation of a
trust product's landing page is worse than no translation.

### 7.4 Adding a language

1. Copy an existing `README.<tag>.md`, translate every span, keep the
   pins as they are (the source has not changed).
2. Add the language to the row under the `# Probavi` heading in
   `README.md` and to the row in every other translation.
3. Run `go test ./internal/docs/` — the §7.3 gates must pass.

Terminology follows the shipped CLI catalog for the same language, so
the README and the terminal agree on what a drill, a sandbox, and an
evidence record are called.

## 8. Terminology and typography

Decided 2026-08-05, from the first full linguistic review of all shipped
catalogs and README translations. These rules bind translators and
reviewers; they are what the §4 and §7.3 gates cannot check by machine.

### 8.1 Keep the product's distinctions distinct

A translation renders meaning, not words. Where English separates two
product concepts, the target language must separate them too — even if
that means departing from the source wording.

- **drill vs. game-day.** A *drill* is one restore proof; a *game-day*
  is an exercise made of drills. Most European languages have one
  natural word for both ("exercise"), which is how nineteen catalogs
  came to call them the same thing. The rule: translate *drill* with
  the language's own word, and where that word would collide, name the
  game-day **`game-day`** — the term is already untranslated in every
  catalog. English's "it identifies the exercise in the summary" is
  therefore rendered "…identifies the *game-day* in the summary".
- **restore vs. recovery.** *Restore* is the act Probavi performs;
  *recoverability* is the property it proves about the organisation.
  Where a language has both words (Hungarian *visszaállítás* /
  *helyreállíthatóság*, German *Restore* / *Wiederherstellbarkeit*),
  use both, consistently, in the catalog and the README alike.
- **conformance checks vs. drill checks.** The frozen protocol checks of
  `adapter conformance` are not the validation checks a drill runs.
  Languages that would use one noun for both take a distinct noun for
  conformance (French *contrôles de conformité* against *vérifications*,
  Italian *controlli* against *verifiche*).
- **`wall-clock`** carries information — the limit is on real elapsed
  time, not CPU time — and must survive translation, not be flattened to
  "time limit".

### 8.2 Typography

- **Quotation marks.** README translations use the target language's own
  convention (German `„…“`, Hungarian `„…”`, French `« … »`, Spanish
  `«…»`). Catalog values do **not**: the quotes there enclose config
  tokens the operator types (`"postgres"`, `"24h"`), so they stay ASCII
  in every language.
- **French spacing.** `README.<tag>.md` is rendered HTML and takes the
  non-breaking space (U+00A0) before `;` `:` `!` `?` and inside `« »`.
  The catalogs do not: terminal output is grepped and copied, and a
  U+00A0 in a diagnostic breaks both. Command-locator prefixes
  (`probavi run:`) keep their tight ASCII colon in every language —
  they are locators, not prose (§1).
